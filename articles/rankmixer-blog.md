# RankMixer 论文解读：参数扩大约 70 倍，工业推荐排序如何维持毫秒级延迟？

推荐模型的规模化，最终要回答一个实际问题：更大的模型能否在严格的在线延迟和成本预算下，带来持续的效果收益？

字节跳动的 RankMixer 给出了一组值得关注的结果：相对于 15.8M 参数的线上基线，1.1B 参数的排序模型将参数规模扩大约 70 倍，报告的推理延迟从 14.5 ms 变为 14.3 ms。与此同时，抖音主端整体用户活跃天数提升 0.2908%，App 使用时长提升 1.0836%。这些是论文报告的特定生产系统实验结果，并非任意硬件上都能直接复现的性能承诺。[论文表 4、表 6](https://arxiv.org/pdf/2507.15551v3)

支撑这组结果的，是一套围绕推荐特征与 GPU 执行效率共同设计的架构：用多头 Token Mixing 交换特征，用 Per-token FFN 分配模型容量，再通过稀疏 MoE 探索更高的参数与计算比。

本文依据用户提供的《RankMixer: Scaling Up Ranking Models in Industrial Recommenders》arXiv v3（2025 年 7 月 26 日）撰写。实验数字均来自该版本，示例、伪代码和公式推导用于辅助理解，不代表作者开源实现或独立复现实验。

**先看清问题：参数量、FLOPs 和延迟是三个指标**

推荐排序模型通常接收数百个异构特征：用户 ID、视频 ID、作者 ID、统计特征、行为序列表示，以及用户与候选之间的交叉特征。模型需要综合这些信息，预测完播、跳过、点赞等行为。

如果直接把原有 MLP 加宽或把交叉模块堆得更深，参数确实会增加，但收益未必按预期增长。论文指出，许多传统特征交叉结构由 CPU 时代的设计演化而来；在 GPU 上，访存、碎片化算子和执行开销可能限制计算效率。

因此，衡量扩大模型的代价，至少需要区分三件事：

| 指标 | 解释 | 不能直接推出什么 |
|---|---|---|
| 参数量 | 模型保存了多少可学习参数 | 参数多不意味着每次请求都激活全部参数 |
| FLOPs | 一次指定计算过程需要多少浮点运算 | 运算少不一定延迟低 |
| 实测延迟与吞吐 | 软硬件系统实际完成工作的速度 | 不能仅由参数量推断 |

RankMixer 用 MFU（Model FLOPs Utilization）描述模型实际利用硬件理论浮点吞吐能力的程度。一个 FLOPs 更高但主要执行大矩阵乘法的模型，可能比 FLOPs 较低、却受访存和小算子限制的模型更快。论文的设计由此转向：把模型容量放在容易被 GPU 高效执行的结构上。[论文 §1、§4.6](https://arxiv.org/pdf/2507.15551v3)

**从异构特征到 Token：先决定信息如何分组**

RankMixer 改造的是排序模型的特征交互主干。原始 ID 仍然需要 Embedding，行为序列也先经过序列模块得到表示；这篇论文没有把全部用户行为直接变成语言模型式的词序列。

它首先按照语义关系和领域知识组织特征。例如，用户侧信息、候选侧信息、序列兴趣和交叉特征可以形成不同的语义组合。随后按照论文的构造方式拼接、分段，再投影到统一隐藏维度 D，得到 T 个 feature token：

```text
用户特征、候选特征、序列表示、交叉特征
                    ↓
       语义组织 → 拼接与分段 → 线性投影
                    ↓
              X，形状 [B, T, D]
```

B 是 batch 大小。这里的 token 是一个特征向量块，不是自然语言中的一个词。

Token 数量涉及建模与执行效率的权衡。若每个字段都独占一个 token，数百个 token 可能让单个计算块太小，也把容量分得过碎；若把全部输入压成一个 token，模型又接近普通 DNN，难以保留不同特征子空间的独立处理能力。

语义分组并不保证只有一种正确方案。论文给出的是一种组织输入的原则，没有披露可直接迁移到所有业务的完整分组规则。[论文 §3.2]

**Token Mixing：通过重排，让每个输出看到所有输入**

RankMixer 的交互模块不计算 Q、K、V，也不构造输入相关的注意力权重矩阵。它先将每个 token 的 D 维向量切成 H 份，然后将不同 token 的同一份拼到一起。

设输入有 3 个 token，每个 token 有 6 维，并令 H = T = 3。将两维视为一组：

```text
输入：
x1 = [a1 | a2 | a3]
x2 = [b1 | b2 | b3]
x3 = [c1 | c2 | c3]

每个 a、b、c 块都有 2 维。

重排后：
s1 = [a1 | b1 | c1]
s2 = [a2 | b2 | c2]
s3 = [a3 | b3 | c3]
```

每个输出 token 都取得了所有输入 token 的一部分信息。对应论文公式：

```text
s_h = Concat(x_1^(h), x_2^(h), ..., x_T^(h))
```

一般情况下，输出形状是 [B, H, T·D/H]。论文设置 H = T，使输出恢复为 [B, T, D]，便于做残差连接。D 也需要能被 H 整除。

用 PyTorch 风格的伪代码表达，就是：

```python
# 仅解释重排过程，省略残差、LayerNorm 和底层性能优化。
B, T, D = x.shape
H = T
mixed = (
    x.reshape(B, T, H, D // H)
     .transpose(1, 2)
     .reshape(B, H, T * D // H)
)
```

这个模块没有可学习参数，但并不等于没有运行成本：转置后的内存布局调整仍可能产生数据搬运。它的优势是没有注意力权重计算，逻辑结构也更简单。

更关键的是，重排本身只是重新组织信息；后面的非线性网络才负责学习这些信息之间的关系。因此，理解 RankMixer 时，应把 Token Mixing 与 FFN 看成配合工作的两部分。

论文认为，推荐特征来自异构空间，直接学习跨空间的内积相似度较困难；其消融实验中，自注意力替代方案也没有取得更好结果。这支持了该实验设置下的选择，但不足以推出“Attention 不适合所有推荐任务”。尤其行为序列建模与本文的异构字段交互，不应混为一谈。[论文 §3.3.1、表 3]

**Per-token FFN：每个位置拥有自己的参数**

完成信息重排后，RankMixer 为每个 token 配置独立的两层 FFN：

```text
v_t = GELU(s_t W_t,1 + b_t,1) W_t,2 + b_t,2

W_t,1：[D, kD]
W_t,2：[kD, D]
```

k 是中间层扩展比例。不同 token 使用不同的 W_t,1、W_t,2。

如果所有 token 共享 FFN，同一套参数必须兼顾所有位置的输入分布。Per-token FFN 则允许各位置使用专属变换。作者将其动机解释为缓解特征子空间之间的主导问题：高频、强信号字段可能掩盖长尾或弱信号。

这里还有一个容易忽略的细节：经过 Token Mixing 后，每个位置已经混入多个输入来源。因此，“独立建模”是指混合后的 token 位置拥有独立参数，不能机械地说某个 FFN 永远只处理用户年龄或视频类别。

为什么论文称它能够增加参数，而不改变计算复杂度？可以做一个忽略偏置的比较：

| 设计 | 参数量 | 处理 T 个 token 的计算量量级 |
|---|---:|---:|
| 所有 token 共享 FFN | 约 2kD² | O(TkD²) |
| 每个 token 独立 FFN | 约 2kTD² | O(TkD²) |

共享 FFN 虽然只保存一套权重，但仍要对 T 个输入分别计算。独立 FFN 把这些计算分配给不同权重，因此参数存储增加，主矩阵乘法的运算量量级相同。

这不意味着显存占用、优化器状态或内存带宽成本也不变。它说明的是：在固定 T、D、k 的比较中，能够通过取消参数共享，提高参数容量与 FLOPs 的比值。[论文 §3.3.2；上表为据此进行的推导]

**一个完整 Block 如何工作？**

RankMixer 沿用残差连接与 LayerNorm。按照论文公式，一个 block 的执行次序为：

```text
S = LN(TokenMixing(X) + X)
Y = LN(PFFN(S) + S)
```

先交换信息，再用独立 FFN 做非线性变换；两步之后各有残差与归一化。堆叠 L 层后，对最终 token 做均值池化，送入不同任务的预测层。

这条路径把模型拆成清楚的职责：Token Mixing 决定信息流动方式，Per-token FFN 学习变换，任务预测层把表示转成业务行为估计。

论文给出 dense 版本主干的近似规模公式：

```text
参数量 ≈ 2kLTD²
单样本前向 FLOPs ≈ 4kLTD²
```

它们主要计算 FFN 项，不能直接当成包含 Embedding、序列模块、输出层和系统开销的全链路精确成本。

作者比较了增加 token 数 T、宽度 D 和层数 L 的扩展方向。在其测试范围内，相近参数规模下，不同方向的效果接近；从硬件效率看，增加宽度更容易形成较大的矩阵乘法。因此论文使用的配置包括：100M 级别的 D=768、T=16、L=2，以及 1B 级别的 D=1536、T=32、L=2。[论文 §3.1、§3.5、§4.3]

**继续扩大容量：稀疏 MoE 为什么还要改路由？**

独立 FFN 可以进一步替换为专家网络。对某个 token 保存多个专家，但每次推理只激活一部分，从而让总参数量与实际计算量分离。

不过，把传统 Top-k 路由直接搬过来会遇到两个问题。第一，不同 token 的信息量不同，固定激活相同数量的专家可能分配不合理。第二，Per-token 结构本来就有多套参数，再叠加独立专家，一些专家可能很少获得有效训练。

RankMixer 为此结合了两项策略。

ReLU Routing 将路由权重写成：

```text
G_i,j = ReLU(h(s_i)_j)
v_i = Σ_j G_i,j · expert_i,j(s_i)
```

正门值对应激活专家，非正输入被 ReLU 置零。不同 token 可以产生不同数量的有效专家。训练目标加入门值的 L1 正则，并用自适应系数控制平均激活预算：

```text
L = L_task + λ L_reg
L_reg = Σ_i Σ_j G_i,j
```

Dense-training / Sparse-inference 则进一步使用训练与推理两套路由器，仅对推理路由施加稀疏正则。目标是在训练时给予专家更充分的更新，在推理时控制计算量。

两项策略处理的是不同问题：ReLU 路由让计算分配有弹性，密集训练改善专家训练不足。论文的图 3 显示，它们结合后，在较低激活比例下能较好保留 dense 模型效果；正文报告吞吐提升超过 50%。这些结果有其特定实验条件，不能换算成所有平台固定的加速倍数。[论文 §3.4、§4.5]

还需要区分两个结果：论文表 6 的线上 1B 部署，对应摘要所称的 dense 参数模型；稀疏 MoE 是进一步扩容的实验方向。不能把“1B 部署延迟不变”全部归功于稀疏激活，也不能写成论文已经完成 10B 全流量部署。

**实验到底支持了哪些判断？**

论文使用抖音生产数据，包含 300 多个特征，实验数据覆盖两周；训练运行在数百张 GPU 的混合分布式框架上。文中以 AUC、UAUC 衡量完播和跳过任务，以参数、FLOPs、MFU 衡量规模与效率。这是工业私有数据上的研究，不是公开小数据集上的通用排名。

表 1 中部分结果如下。增益栏保留论文的“+x%”记法，不擅自换算成 AUC 绝对值或百分点；FLOPs 使用该表的 batch=512 训练口径：

| 模型 | 参数量（不含稀疏 Embedding） | 训练 FLOPs/Batch | Finish AUC 报告增益 | Skip UAUC 报告增益 |
|---|---:|---:|---:|---:|
| DLRM-MLP-100M | 95M | 185G | +0.15% | 未报告 |
| Wukong | 122M | 442G | +0.29% | +0.65% |
| RankMixer-100M | 107M | 233G | +0.64% | +1.33% |
| RankMixer-1B | 1.1B | 2.1T | +0.95% | +1.82% |

这里的共同参考是表中的 DLRM-MLP 基线，而不是每一行相对上一行的变化。RankMixer-100M 的 FLOPs 低于 Wukong，但高于 DLRM-MLP-100M；准确的结论是，它在这组对比中提供了更好的效果与计算权衡，而非所有指标都最小。

消融结果也解释了架构的分工：移除 Token Mixing，ΔAUC 为 −0.50%；将独立 FFN 改成共享 FFN，为 −0.31%；移除残差和 LayerNorm，分别为 −0.07% 和 −0.05%。表 3 的自注意力替代方案则报告 ΔAUC −0.03%、参数 +16%、FLOPs +71.8%。这些数字使用各自表格的对照条件，不宜跨表直接相加。[论文表 1—3]

**约 70 倍参数，为何没有带来约 70 倍延迟？**

表 6 是理解论文部署结果的关键：

| 指标 | 线上基线 | RankMixer-1B |
|---|---:|---:|
| 参数量 | 15.8M | 1.1B |
| FLOPs（表 6 口径） | 107G | 2106G |
| MFU | 4.47% | 44.57% |
| 计算精度 | FP32 | FP16 |
| 推理延迟 | 14.5 ms | 14.3 ms |

作者从三方面解释成本：每参数对应的 FLOPs 降低约 3.6 倍，MFU 提高约 10 倍，以及该部署条件下 FP16 理论浮点吞吐相对 FP32 提高约 2 倍。较大的 GEMM、并行 FFN 的 kernel 融合，以及减少访存和执行开销，共同提高了实际计算效率。

论文将其概括为一个近似关系：

```text
计算时间 ≈ FLOPs /（MFU × 硬件理论浮点吞吐）
```

它适合解释主要计算部分，但不完整覆盖在线请求排队、跨设备通信、Embedding 查询和尾延迟。FP16 的实际收益也依赖硬件与算子配置。

按表 6 的原始数值，2106/107≈19.7，而表内 Change 栏写的是 20.7×；这是该版本的一处数字不一致。因此更稳妥的表述是“FLOPs 增长约 20 倍”，不要把表中的所有倍率当作可以无误相乘的恒等式。[论文 §4.6、表 6]

**线上收益与结论边界**

抖音主端整体用户的报告结果包括：活跃天数 +0.2908%、使用时长 +1.0836%、点赞 +2.3852%。低活跃用户的活跃天数提升为 +1.7412%，高于整体人群。广告场景报告 ΔAUC +0.73%、ADVV +3.90%；ADVV 在文中指 Advertiser Value，不能直接改写为平台收入增长。[论文表 4—5]

这些结果说明，作者报告的收益已从离线预测指标延伸到线上业务指标。不过，阅读时仍应保留几条边界：

- 活跃天数不是 DAU 的同义词，不能把相应提升直接写成 DAU 增长。
- 低活跃用户收益较高，不等于已经严格证明了冷启动能力。
- 性能结果依赖私有特征、海量训练数据、分布式框架及底层优化，仅复刻网络层不能保证复现部署成本。
- 文中的 scaling 曲线描述了所测范围内的扩展趋势，未构成对任意规模收益的保证。
- Token Mixing 的重排本身没有参数，模型整体仍依赖可训练投影、独立 FFN 和任务层；“无参数交互”不能简化成“模型不需要学习”。

从模型设计角度看，RankMixer 最值得借鉴的是容量分配的方式：先组织好异构输入，用简单的信息交换连接各特征位置，再把可学习参数放进独立、可并行的大矩阵计算中。对于准备扩展排序模型的团队，一个有价值的起点是同时测量效果、FLOPs、MFU 和实际延迟，并通过消融区分结构收益与扩容收益。这样才能判断新增参数究竟转化成了更好的建模能力，还是更高的运行成本。
